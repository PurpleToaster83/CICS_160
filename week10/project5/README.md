# CICS 160 Object Oriented Programming Project 5
The original code was written in a way so that it could accept multiple wizards and/or dragons just by changing the entities array in GameDriver.java. This was achieved by using for loops in the main function of the GameDriver class that looped over the entities and type checked to take turns based on the interface they implemented.

For part 7, I implemented a new AIControlled class: A Goblin. Goblin.java extends CombatEntity and implements AIControlled, so GameDriver treats it the same as it would a Dragon (or any other AIControlled type). In Goblin's takeTurn method, there is a possibility that the Goblin temporarily summons a "swarm" of other goblins to attack. The attacking of the summoned goblins is handled by the takeTurn function of the original goblin so as to not have to add and remove entities. This decision was made because a real summon would require the Goblin class to hold a reference to the array storing entities or additional methods, which could violate the Dependency Inversion Principle. The only difference between the new and old GameDriver classes is a result of adding a Goblin character to the entities array.

Overall, it was pretty smooth implementing the Goblin class into the code base because of the original GameDriver code loops over the roster and checks the interface instead of hardcoding entity turns. The Goblin class can be used anywhere that the other AIControlled implementor, the Dragon class, is used, following the Lisckov Substitution Principle. The interfaces used in the project are small, so that they don't force methods and attributes onto classes per the Interface Segregation Principle. The Open/Closed principle was followed closely in the code because I was able to add a whole new class by only adding a Goblin to the entities array and writing the class code. Lastly, the code base follows the Single Responsibility Principle because each class owns its own behavior while the driver coordinates actions.
